# Brechas de arquitectura para una BApp diferencial

Fecha: 29-09-2026. **Revisión de lo implementado, no dictamen de PortSwigger.** El producto prioritario ahora es una web de equipo desplegable; la extensión Burp viene después. La entrega exacta del 31-10 sigue sujeta al gate de capacidad y fuente pasiva. Estas brechas se investigan sin prometer aceptación. Base de lectura: código y pruebas de `extensions/burp`, núcleo TypeScript, [contrato snapshot](../contracts/README.md), [HTTP propuesto](../contracts/http-observation.schema.json), [modelo de amenazas](../security/threat-model.md) y [checklist BApp](../bapp/acceptance.md). [Criterios oficiales](https://portswigger.net/burp/documentation/desktop/extend-burp/extensions/creating/bapp-store-acceptance-criteria) consultados el 29-09-2026.

## Lo que hoy impediría defender la propuesta

1. **No existe la tarea BApp completa.** El JAR Java toma una selección acotada de requests en scope y produce metadatos HTTP en una pestaña de texto. No carga Nmap XML, no ingiere el `Snapshot 1.0.0`, no correlaciona evidencia Nmap+HTTP y no ofrece una explicación navegable de una relación. La funcionalidad se parece más a un spike de normalización que a CHEF como producto. Un build correcto no demuestra valor dentro de Burp.
2. **Pasivo y activo no forman un flujo único.** El pasivo actual es selección manual de requests, no una captura/actualización automática probada. No hay adaptador de reconocimiento activo. Antes de activarlo, definir consentimiento, alcance por IP/host/puerto, rate limit, redirects, timeouts, cancelación y uso de la red de Burp; el XML importado no autoriza sondeos. No probar redes ajenas con base en una inferencia del grafo.
3. **Los contratos no convergen aún.** Nmap produce snapshot `1.0.0` con dirección/servicio; Montoya produce envelope HTTP propuesto `1.1.0` con origin/método/hash de path. Falta un contrato de ingestión y reglas versionadas que expliquen cuándo una request corresponde a un servicio observado, sin unir hosts por hostname, IP compartida, virtual host o DNS no verificado. Hace falta conservar observaciones independientes y provenance en cada relación. Un SHA-256 de metadatos normalizados no es hash del tráfico crudo ni prueba autenticidad.
4. **Fronteras TS/Go/Java deben conservar semántica.** Hoy el núcleo Nmap/CLI es TypeScript/Node y Burp usa Java; el motor web Go está propuesto, no implementado. Montoya no puede ejecutar directamente clases TypeScript ni reglas Go. Una BApp instalable y útil sin servicio acompañante necesitaría un subset autónomo Java o una integración opcional justificada, con fixtures de conformidad para identidad, scope, referencias y errores. Obligar al usuario a instalar Node/Go o una web local agregaría dependencias que tendrían que justificarse frente a los criterios de PortSwigger.
5. **Robustez y experiencia no están validadas.** Faltan pruebas manuales de carga, descarga repetida, latencia en EDT, proyectos grandes, uso offline y compatibilidad de versión mínima de Burp. El handler copia metadatos de hasta 100 requests antes de pasarlos al worker: está acotado, pero su impacto en UI no se ha medido. La pestaña de texto no demuestra selección/evidencia eficiente ni ahorro de tiempo. Véase [matriz pendiente](../bapp/manual-tests.md).
6. **Diferenciación y beneficio siguen siendo hipótesis.** [NMAP Parser](https://portswigger.net/bappstore/0780c0a9f12e47848a94ac3e43dccbd9) ya importa XML y [Nmap Scanner](https://portswigger.net/bappstore/9710f65c31044b3794df0767f8f4bd5d) integra escaneos. [Burp Scanner](https://portswigger.net/burp/documentation/scanner/crawling) ya representa navegación. Un importador, un botón de scan o un grafo por sí solos no establecen novedad. La propuesta propia es reducir tiempo/errores al explicar una relación **entre fuentes** con evidencia reproducible; aún falta medirlo con operadores.

## Secuencia de evidencia posterior a la demo

Primero validar un caso pasivo Nmap+request sintético en un modelo común con golden tests Java/TypeScript y un control negativo de host compartido. Luego construir dentro de Burp una tarea autónoma: importar evidencia Nmap local, elegir requests en scope, ver por qué se relacionan, inspeccionar sus dos cadenas de evidencia y exportar. Después ejecutar la matriz manual y medir tiempo/error contra herramientas cercanas con usuarios y tareas equivalentes. Solo tras esa prueba evaluar si un adaptador activo aporta valor adicional y si se puede operar con límites y autorización verificables. Revisar versiones, licencias, dependencias y criterios de PortSwigger justo antes de postular.

La arquitectura React/TypeScript + PostgreSQL/Prisma es el producto prioritario, pero Java/Montoya no ejecuta directamente ese núcleo. La BApp posterior deberá definir si opera autónoma con subset de reglas y fixtures de conformidad, o si se integra opcionalmente con el servicio web; cada opción tiene coste de instalación, conectividad y privacidad. Ni la web ni este documento prueban aceptación en BApp Store.
