# Investigación de reconocimiento y correlación para CHEF

Consultada el 29-09-2026. **Hechos de fuentes primarias, inferencias de diseño y resultados medidos se separan.** Esta revisión no ejecutó escaneos ni consultó objetivos externos. El inventario fechado está en [sources.json](sources.json); la [propuesta](../proposals/2026-09-scope-decision.md) pide decisión antes de cambiar ADRs.

## Evidencia disponible y qué significa

- **Activo importado:** [Nmap XML](https://nmap.org/book/output-formats-xml-output.html) ofrece hosts, puertos, estados y metadatos estructurados. “Activo” describe cómo fue obtenida esa evidencia por la herramienta originaria; CHEF en esta fase **solo importa** archivos autorizados. [Los seis estados de puerto](https://nmap.org/book/man-port-scanning-basics.html) dependen del punto/instante de observación. `open|filtered` no es `open`; servicio sugerido por número de puerto no equivale a versión verificada. Mantener hora, scope, comando si está disponible, host, protocolo, estado, service y origen XML. El parser actual solo admite su subset declarado.
- **Pasivo candidato:** [Certificate Transparency](https://www.rfc-editor.org/rfc/rfc9162.html) documenta certificados emitidos u observados en logs; un nombre de certificado es pista histórica, no prueba de control actual ni servicio vivo. [RDAP JSON](https://www.rfc-editor.org/rfc/rfc9083.html) describe respuestas de registro, con posibles datos redactados y distinta frescura. Una captura HTTP autorizada sería evidencia pasiva del tráfico visto, pero el fixture Montoya actual no está integrado al core. Ningún proveedor/API ni credencial para el primer conector está confirmado.
- **Límite entre pasivo y activo:** [ZAP distingue escaneo pasivo de activo](https://www.zaproxy.org/getting-started/) y advierte que el activo afecta objetivos. La demo aprobada importa resultados; no hay ejecución de Nmap, crawl, DNS probing o HTTP dirigido desde CHEF. Consultar una API OSINT externa también requiere revisar términos, datos enviados y permiso, aunque no sondee el objetivo directamente.

No se dispone todavía de credenciales, acceso garantizado ni permiso de uso para esos proveedores. “Consumir todas las APIs” crearía un sistema frágil: elegir **una** fuente para la primera vertical según autorización, calidad temporal, coste, utilidad de unión con Nmap y reproducibilidad; añadir otras por adaptadores con tests de contrato, backoff, límites, procedencia y degradación visible. No enviar dominios de clientes a terceros por defecto. Un dato externo antiguo se presenta como evidencia histórica, no actualización en tiempo real.

## Algoritmo propuesto: observación → candidato → relación explicada

1. **Ingesta inmutable e idempotente.** Guardar digest del archivo, run, locator por registro y payload mínimo seguro. Registrar resumen de descartes por `fuera_de_scope`, `no_soportado`, `duplicado_exacto`, `estado_no_prioritario`, sin borrarlos silenciosamente. Vista de trabajo filtra, exportación auditada conserva evidencia permitida. Importar dos veces el mismo archivo/proyecto debe ser idempotente, con historial de run separado cuando proceda.
2. **Normalización tipada.** Canonicalizar DNS (case/IDNA según contrato), IP (IPv4/IPv6), servicio (IP + transporte + puerto) y URL/origin en adaptadores versionados. Jamás fusionar `hostname == host`, IP compartida, banner, ASN o certificado como identidad de una organización. Separar entidad, observación y afirmación relacional.
3. **Bloqueo de candidatos.** Comparar solo claves compatibles dentro de proyecto/scope y ventana temporal pertinente. Igualdad exacta de clave tipada crea una unión mecánica; distintas fuentes que afirman el mismo dominio/IP generan **corroboración** con dos procedencias, no una “verdad” sin contexto. DNS↔IP puede cambiar por tiempo y CDN; mostrar relación fechada, nunca propiedad permanente. Un mismo hostname en dos hosts del fixture sigue separado.
4. **Regla versionada.** Cada enlace conserva `ruleId`, versión, evidencias que apoyan/contradicen, `observedAt`, aserción (`observed`, `inferred`, `candidate`) y motivo legible. Falso positivo revisado se marca/suprime de la vista, sin borrar observaciones originales. Una importación posterior puede refrescar o contradecir, no sobrescribir historia.
5. **Prioridad explicable.** Rankear para atención por nueva evidencia, estado observado, corroboración independiente, frescura y contradicción; no inferir severidad/vulnerabilidad desde puerto abierto. Exponer filtros antes que una “puntuación de riesgo” opaca.

La cadena de procedencia se inspira en [PROV-O](https://www.w3.org/TR/prov-o/), pero CHEF no afirma implementar el estándar. [Fellegi–Sunter](https://www.tandfonline.com/doi/full/10.1080/01621459.1969.10501049) permite probabilidades de enlaces con comparaciones calibradas; [Splink explica](https://moj-analytical-services.github.io/splink/topic_guides/theory/probabilistic_vs_deterministic.html) ventajas y supuestos. Para este dominio, un score probabilístico sin etiquetas de verdad de referencia daría precisión falsa. Alternativa A es reglas deterministas auditables; B es sugerencias probabilísticas más tarde, con conjunto etiquetado, curvas de precisión/recobrado y revisión humana. No usar embeddings/LLM para auto-fusión de identidades.

## Diseño de datos y contratos

Propuesta para PostgreSQL/Prisma: `User`, `Project`, `Membership`, `ScopePolicy`, `Source`, `ImportRun`, `EvidenceBlobMetadata`, `Observation`, `Entity`, `RelationAssertion`, `ReviewDecision`, `Export`. Las filas de datos incluyen `projectId`, fechas y versión de parser/regla. Almacenar payloads sensibles solo según política de retención definida; el hash no los anonimiza. Índices por proyecto, clave tipada, tiempo y fuente; constraints para idempotencia. El dominio sigue siendo independiente: puerto `ObservationRepository`/unidad de trabajo en application, adaptador Prisma en `packages/adapters`. `Snapshot 1.0.0` es contrato de intercambio; un export rico multifuente puede requerir versión nueva con schema, ejemplo, prueba y compatibilidad. No mapear tablas 1:1 al wire por conveniencia.

[Prisma ORM con PostgreSQL](https://www.prisma.io/docs/prisma-orm/quickstart/postgresql) está documentado para TypeScript/Node. Un backend Go sería otra decisión técnica: el [cliente Go de Prisma anuncia deprecación y ausencia de soporte para Prisma v7+](https://github.com/prisma/prisma-client-go). Dado el núcleo TypeScript ya probado, TypeScript/Node minimiza reimplementación; si Go es obligatorio, comparar explícitamente puente por servicio frente a reescritura/ORM alternativo y reestimar. La decisión está pendiente de confirmación del propietario.

## Interfaz y operación propuestas

Dirección visual: **mesa de análisis de evidencia**, no estética genérica “hacker”. Encabezado con proyecto y momento de última actualización; panel izquierdo con fuentes, estado y filtros; centro con lista/grafo de activos y relaciones; panel derecho con explicación, evidencia/locator y controles de revisión. Cada nodo/relación tiene equivalente en lista navegable por teclado. Estados vacíos, carga, error, fuente caducada y evidencia conflictiva son parte del diseño. Colores semánticos discretos y texto: azul tinta `#16324F`, fondo `#F7F5F0`, énfasis `#D27A38`, observado `#25705A`, candidato `#9A5A32`, alerta `#A33839`; contraste y foco se validarán en UI real. La UI no recalcula identidad y no interpreta HTML importado.

Propuesta de despliegue para equipo: React/Vite en [Vercel](https://vercel.com/docs/frameworks/frontend/vite), API Node/TypeScript y PostgreSQL en [Railway](https://docs.railway.com/guides/saas-backend). Configurar origen/CORS, cookies seguras, OAuth callback, variables secretas, migraciones, backups y pruebas entre proyectos antes de exponer datos. “Tenemos acceso” a plataformas no confirma presupuesto ni despliegue configurado. OAuth autentica; CHEF autoriza, registra membresía y audita exportaciones. [GitHub OAuth](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps) y [prácticas oficiales](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/best-practices-for-creating-an-oauth-app) sustentan el flujo. PostgreSQL [RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) puede reforzar aislamiento, con tests para el contexto de cada solicitud.

No llamar “tiempo real” a una carga manual. Fase 1: actualización por importación/consulta con `lastObservedAt` visible. Fase 2: refresco asíncrono de fuente autorizada con latencia/fallas medidas. Fase 3: eventos al cliente si aportan valor; no comprometer SSE antes de medir. Un job activo futuro requiere autorización de scope, revisión de destinos/redirects, egress restringido, cuotas, aislamiento y cancelación; nunca se deriva scope del archivo importado.

## Comparación y experimento

[Amass](https://github.com/owasp-amass/amass) ya distingue rutas pasivas/activas, [SpiderFoot](https://github.com/smicallef/spiderfoot) ofrece módulos/visualización y [Uncover](https://github.com/projectdiscovery/uncover) agrega proveedores de búsqueda. Por ello el diferencial es una **hipótesis**: menos pasos/tiempo para responder “qué sabemos, por qué lo enlazamos y qué es dudoso” en un proyecto autorizado. Con 5–8 evaluadores, comparar contra revisión manual del mismo XML + fuente pasiva; ordenar tareas de forma contrabalanceada, fijar respuestas correctas antes, recoger tiempos, pasos, errores, falsos enlaces y completitud de evidencia. La métrica inicial propuesta es ≥30 % menos tiempo mediano sin aumentar falsos enlaces; una muestra pequeña es indicio, no validación comercial. Sin fuente pasiva confirmada, solo se podrá ensayar un caso sintético y etiquetarlo como tal.

## Huecos que bloquean la ruta vertical

Faltan fuente pasiva y permiso de uso; contrato y labels de fixture multifuente; backend Go vs TypeScript/Prisma; corte de despliegue del 31-10; política de datos/retención; presupuesto de Vercel/Railway; piloto y rúbrica; diseño concreto de roles y scopes de proyecto. Resolverlos en ese orden antes de prometer integración o medición real. La CLI, schema, pruebas y fixture Nmap actuales quedan como base de regresión.
