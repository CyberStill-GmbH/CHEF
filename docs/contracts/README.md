# Contratos

La prioridad web se discute en el [borrador de API multiusuario](web-api-proposal.md). La [API loopback](api.md) y los [eventos SSE](events.md) son diseños históricos no implementados; **no son contratos estables**. Los formatos ejecutables actuales son Snapshot 1.0.0 para Nmap y Snapshot 1.1.0 para la ingestión offline de BBOT, además del envelope HTTP separado del spike Montoya.

`snapshot.schema.json` es la autoridad wire del incremento offline, JSON Schema 2020-12. Mantiene snapshots Nmap `1.0.0` y añade `1.1.0` para evidencia importada desde BBOT JSONL; los tipos del dominio deben concordar mediante pruebas. `Asset`, `Evidence`, `Observation`, `Relationship`, `ExposurePath`, `ScanRun` y `ScopePolicy` tienen campos requeridos y propiedades extra prohibidas. `Finding` está definido como contrato reservado; el motor actual no lo produce.

## Semántica

- Asset: entidad estable; firstSeen/lastSeen son tiempos observados, no reloj de importación; ≥1 Observation.
- Observation: hecho `open-port`, source/version/run y locator dentro del archivo; una Evidence; timestamps UTC RFC3339. `1.0.0` acepta `nmap-xml`; `1.1.0` acepta `bbot-ndjson`.
- Evidence: SHA-256 de bytes, parserVersion, importedAt y locator raíz. No incorpora raw sensible ni ruta de filesystem. Reimportar idénticos bytes/scope/versión produce los mismos IDs.
- Relationship: exactamente dos Asset existentes; ≥1 Observation existente, assertion observed.
- ExposurePath: en v1 exactamente dos assets y una relación; assertion inferred, regla open-service/v1, vulnerabilidad confirmada siempre false.
- ScanRun: snapshot publicado únicamente al completarse; IDs deterministas por bytes/scope/parser. La API futura manejará intentos cancelados/fallidos con IDs independientes.
- ScopePolicy: allowlist de IP/CIDR, exclusiones con precedencia, puertos/protocolos y límites. Importar un archivo no autoriza tráfico ni modifica la policy.
- Finding reservado: necesita evidence vía Observation y revisión humana; todavía sin API/implementación. Un puerto abierto no genera Finding.

Confianza 0..1: en v1 describe fidelidad al reporte importado. No está calibrada estadísticamente. La fusión usa máximo sin interpretar duplicados como evidencia independiente. Conservar contradicciones/estado closed en futuras versiones requiere nuevo tipo de Observation.

## Identidad y fusión

SHA-256 de JSON de una lista ordenada de partes UTF-8; prefijo asset/observation/evidence/run/relationship/path. No concatenar campos ambiguos sin delimitación. Keys address/service se documentan en SOLID. Scope normaliza y ordena sus arrays antes de hashing. Golden fixture fija IDs para evitar divergencia Java/TS.

Schema verifica forma, no integridad referencial ni autoría. Pruebas del pipeline verifican referencias; importación de snapshots externos requerirá un verificador semántico antes de persistirlos. Los exporters actuales solo emiten resultados del pipeline validado.

## Ejemplos y compatibilidad

`event-statistics.schema.json` define el DTO IPC `1.0.0` que acompaña una importación local BBOT: conteos deterministas por tipo y productor. El comando no modifica `Snapshot 1.1.0` y su respuesta es independiente; clientes que no consumen el comando siguen usando snapshots sin cambios. La vista no es un reporte de ejecución en vivo: los contadores de consumo y velocidad requieren un ciclo de ejecución que aún no se integra en Tauri. El ejemplo contiene los tres eventos sintéticos del fixture CHEF.

[Scope ejecutable](../../fixtures/scope/lab.json), [Nmap sintético](../../fixtures/nmap/lab.xml), [eventos JSONL de importación](../../fixtures/event-import/events.ndjson), [snapshot ejemplo 1.0](examples/snapshot.json), [snapshot ejemplo 1.1](examples/event-snapshot.json), [grafo de reconocimiento CHEF 1.4.0](examples/recon-graph.json) con [su esquema](recon-graph.schema.json) y [resumen de estadísticas](examples/event-statistics.json). `npm run check:docs` valida los ejemplos de los contratos registrados.

La acción local `export_chef_snapshot` recupera desde SurrealDB un snapshot validado por `runId`; el frontend lo descarga como JSON usando el contrato Snapshot existente. No crea un formato de exportación ni modifica la versión del esquema. El JSONL BBOT de origen queda almacenado aparte para preservar procedencia y linaje.

`export_chef_observed_domains` adapta `modules/output/subdomains.py` al grafo CHEF y publica `observed-domain-export 1.0.0` ([esquema](observed-domain-export.schema.json), [ejemplo](examples/observed-domain-export.json)). Incluye únicamente dominios con evidencia directa `DNS_NAME`, ordenados de forma determinista, y conserva IDs/fechas de esos eventos. Excluye `DNS_NAME_UNRESOLVED` y las pistas `DNS_NAME_HINT`; `scopeStatus: not_asserted` deja claro que el grafo no acredita el filtro `in_scope_only` de BBOT. La exportación no confirma resolución actual, alcance ni propiedad y no contiene datos crudos. Los consumidores de Snapshot y del grafo existente no cambian; este DTO de exportación es un contrato nuevo `1.0.0`. La prueba funcional de selección, orden, evidencia y control negativo queda pendiente para la fase indicada por el propietario.

`export_chef_evidence_csv` adapta parcialmente `modules/output/csv.py` mediante `evidence-csv-export 1.0.0` ([esquema](evidence-csv-export.schema.json), [ejemplo](examples/evidence-csv-export.json)). Emite filas deterministas por vínculo de activo/evidencia y preserva también evidencia todavía no proyectada a un activo CHEF, junto con IDs, tipo, fecha, localizador y linaje padre. Omite el nombre de módulo porque el JSONL importado no acredita que sea un identificador de origen confiable. Las columnas se fijan en CHEF; no incluye payloads originales, tags, `scope_distance`, IPs resueltas ni rutas de descubrimiento que CHEF no pueda demostrar. Conserva claves de activos CHEF ya proyectadas. Las celdas potencialmente interpretables como fórmulas se anteponen con apóstrofo antes del escape CSV. La capa de dominio solo construye bytes en memoria; Tauri recupera el grafo local y la interfaz descarga el archivo. La salida declara `scopeStatus: not_asserted`. No reproduce columnas dinámicas, append/backups ni escritura a disco del módulo de origen. La prueba funcional de orden, escape CSV, neutralización y límites queda pendiente para la fase indicada por el propietario.

`export_chef_nmap_evidence` adapta parcialmente `modules/output/nmap_xml.py` con `nmap-evidence-export 1.0.0` ([esquema](nmap-evidence-export.schema.json), [ejemplo](examples/nmap-evidence-export.json)). Produce XML CHEF con vocabulario inspirado en Nmap y `scanner="chef"`; **no cumple el DTD oficial de Nmap ni garantiza interoperabilidad con sus herramientas**. Incluye solo relaciones observadas IP→servicio con calificación `observed_open` y evidencia directa concordante `OPEN_TCP_PORT` o `OPEN_UDP_PORT`. La IP también debe ser una entidad observada, no una pista. Incluir UDP es una extensión CHEF: el módulo de origen escucha únicamente puertos TCP. `observationStart`/`observationEnd` describen el intervalo de evidencia importada; `start`/`startstr` usan el inicio como ancla del subset, no como hora de comienzo de un escaneo. Se omite `runstats`: CHEF no conoce objetivos negativos, duración completa ni resultado de un escaneo. No crea hostnames mediante resolución separada, ni incluye banners, técnica, argumentos, `scaninfo` o IPs obtenidas solo desde `resolved_hosts`. El contrato declara `scopeStatus: not_asserted`; el formato no se reimporta con el lector CHEF de XML Nmap, que exige `scanner="nmap"`. Tauri lee el grafo local y React descarga el XML; no hay tráfico de red. La verificación funcional de XML, asociaciones positivas y exclusión de pistas queda pendiente para la fase indicada por el propietario.

`export_chef_asset_inventory` adapta parcialmente `modules/output/asset_inventory.py` con `asset-inventory-export 1.0.0` ([esquema](asset-inventory-export.schema.json), [ejemplo](examples/asset-inventory-export.json)). Emite una fila determinista por host observado (dominio o IP), con arrays JSON en celdas CSV para IPs, puertos TCP/UDP abiertos, endpoints, tecnologías, IDs de hallazgos candidatos y IDs de evidencia; cada asociación requiere una relación CHEF observada/candidata y evidencia compartida concordante. La clave de un candidato es un digest, no una descripción; el contrato identifica ese campo como IDs y no expone el payload del evento. Las filas y el archivo están acotados. `scopeStatus` es `not_asserted`: el grafo no conserva `in_scope` del módulo fuente. No agrupa IPs como internas/externas ni importa `resolved_hosts` sin relación explícita. Omite proveedor, título/estado HTTP, WAF, RR DNS, campos personalizados y puntaje de riesgo, porque el grafo CHEF no los acredita como atributos de host. Los eventos `FINDING` permanecen como candidatos, nunca como vulnerabilidades confirmadas. No lee/escribe archivos, reutiliza inventarios anteriores ni activa un nuevo escaneo; Tauri recupera el grafo local y React descarga el CSV. La validación funcional de asociaciones, neutralización de fórmulas y límites queda pendiente para la fase indicada por el propietario.

El escritor genérico de `modules/output/txt.py` se excluye: genera un archivo de texto libre con la representación humana de cada evento. CHEF conserva el evento fuente saneado y ofrece descargas estructuradas versionadas; no duplica esa evidencia en otra salida sin esquema. El `scan-log` de Tauri es distinto: comunica fases y conteos del trabajo de importación con mensajes fijos, no es un transcript de eventos ni el reemplazo exacto del archivo TXT. La exportación local de informes legibles se mantiene como decisión pendiente separada.

El módulo `modules/internal/unarchive.py` también se excluye: su comportamiento lee rutas de eventos `FILESYSTEM`, ejecuta `7z`/`tar` y escribe archivos extraídos. CHEF conserva esos eventos como datos no confiables; no ejecuta `7z`/`tar` para extraer su contenido ni interpreta una ruta importada como permiso de filesystem. `modules/internal/base.py` y el `__init__.py` vacío no tienen una adaptación funcional individual; el runtime usa componentes Rust compilados y registro explícito.

`import_bbot_jsonl` recibe por IPC el texto de un archivo `.jsonl`/`.ndjson` (máximo 2 MiB) y un objeto `ScopePolicy 1.0.0` separado. La UI también limita el archivo de política a 64 KiB. Rust valida ambos antes de importar, guarda únicamente los datos saneados por el parser y persiste el snapshot, grafo fuente y proyección CHEF en SurrealDB. `HTTP_RESPONSE` conserva el origen canónico, estado y método, elimina el path y descarta cuerpo, cabeceras y cualquier campo no incluido en la lista permitida; genera evidencia de endpoint observado sin efectuar una solicitud. La operación no inicia descubrimiento de red. Se conserva la estructura y versión de Snapshot y ScopePolicy; una versión de escritorio anterior que no incluya el comando simplemente no ofrece importación local de JSONL.

`ScopePolicy 1.0.0` acepta `allowedAddresses` y `excludedAddresses` con IP literales o redes CIDR. Las redes se normalizan al identificador de red antes del digest; para cada servicio importado se evalúa la IP observada, y cualquier exclusión CIDR prevalece sobre una autorización coincidente. El [ejemplo CIDR](examples/scope-cidr.json) ilustra una red permitida y una subred excluida. Esto filtra datos de una importación local; no concede permiso para generar tráfico. Los archivos previos con IP literales mantienen su comportamiento y su digest.

La proyección `recon-graph 1.2.0` canonicaliza URLs HTTP(S) de activos: host/esquema en forma canónica, puerto por defecto normalizado y query/fragmento retirados según la política local de datos. Para `HTTP_RESPONSE` también se elimina el path y se usa el origen como endpoint observado. La evidencia conserva su evento fuente saneado. La clave determinista del activo puede cambiar al reimportar URLs que antes diferían solo en mayúsculas del host o puerto por defecto; los grafos ya guardados no se reescriben automáticamente.

Para eventos `OPEN_TCP_PORT` y `OPEN_UDP_PORT`, CHEF valida que `data` sea un netloc `host:puerto`, completa `host` o `port` si el export omitió uno, y rechaza valores explícitos que contradigan el netloc. El netloc solo se analiza localmente; no se resuelve el host. Exportaciones que omitan `host`/`port` siguen siendo aceptables si `data` incluye ambos; las que contienen campos inconsistentes se rechazan para no asociar evidencia a un servicio distinto.

El evento interno Tauri `scan-log` usa [scan-log.schema.json](scan-log.schema.json) y los ejemplos [normal](examples/scan-log.json) y [cancelado](examples/scan-log-cancelled.json). La versión `1.2.0` incorpora `requestId` para correlacionar cada invocación y añade la fase `cancelled`; los validadores `1.0.0` y `1.1.0` deben actualizarse para aceptar esta emisión. Solo describe importación offline local: inicio, eventos procesados, validación, guardado, fin, error o cancelación, secuencia, tipo de evento y fecha observada. El mensaje visible es texto fijo CHEF; no transporta host, URL ni datos crudos de evidencia. La cancelación usa el `jobId` de la invocación correlacionada y el comando `cancel_import_job`, cuya respuesta indica si el trabajo seguía cancelable. El adaptador serializa importaciones y rechaza una solicitud simultánea. Solo se acepta cancelar mientras el worker siga procesando y antes de `validated`; el registro del trabajo y la transición a persistencia se coordinan para no confirmar una cancelación tardía. React oculta el botón al llegar a `validated`. La prueba de concurrencia, cancelar durante análisis y rechazar cancelación tras validación queda pendiente para la fase de pruebas indicada por el propietario.

La configuración local se carga mediante `load_chef_config` desde `config.toml` en el directorio de configuración de la aplicación que entrega Tauri. Si no existe, CHEF usa los valores por defecto del dominio; no crea archivos ni copia los valores por defecto de BBOT. El [DTO de configuración](chef-config.schema.json) y [ejemplo](examples/chef-config.json) exponen solo preferencias validadas, sin credenciales. `active_discovery` debe permanecer `false`; un archivo importado no habilita reconocimiento de red. Los campos wire se consideran `1.0.0`; una modificación incompatible requiere nuevo esquema, ejemplo, prueba y nota de compatibilidad. La suite del contrato se deja para la fase posterior indicada por el propietario.

El comando local `parse_chef_target_seed` devuelve target-seed `1.3.0` y conserva lectura de `1.0.0`–`1.2.0`. La versión `1.1.0` incorporó `AS`/`ASN`; `1.2.0`, `ORG`/`ORG_STUB`; y `1.3.0`, `EMAIL_ADDRESS`, `USERNAME`/`USER`, `FILESYSTEM`/`FILE`/`FOLDER`/`DIR`/`PATH`, `MOBILE_APP`/`APK`/`IPA`/`APP` y `BLACKLIST_REGEX`/`RE`. Las etiquetas de organización, usuario, ruta, app y patrón llevan `host: null` y `port: null`; no tocan filesystem, no descargan, no evalúan expresiones regulares y no crean scope. El correo se normaliza localmente y su dominio es solo una pista. ASN no determina que el bloque esté asignado ni expande o consulta sus redes. Véanse los [ejemplos URL `1.0.0`](examples/target-seed.json), [ASN `1.1.0`](examples/target-seed-asn.json), [organización `1.2.0`](examples/target-seed-organization.json), [correo](examples/target-seed-email-address.json), [usuario](examples/target-seed-username.json), [ruta](examples/target-seed-filesystem.json), [app móvil](examples/target-seed-mobile-app.json) y [patrón](examples/target-seed-blacklist-regex.json). El cambio es aditivo; los consumidores antiguos rechazan `1.3.0` hasta actualizar esquema y tipos. Las pruebas funcionales de conformidad se dejan para la fase posterior solicitada; el verificador documental valida los ejemplos contra el esquema.

El cambio `1.1.0` añade la fuente `bbot-ndjson` y su lector offline; `1.0.0` conserva exactamente la semántica Nmap anterior. Los lectores anteriores rechazarán `1.1.0`; los lectores CHEF actuales aceptan ambas versiones y comprueban que la fuente corresponda a la versión. Cambios aditivos posteriores usan versión minor con lector compatible; remover/renombrar campos, alterar identidad o semántica requiere versión mayor. Todo cambio wire incluye esquema, types, fixtures, prueba y nota de compatibilidad.

El parser de eventos usa `parserVersion 1.1.0`: aplica el valor predeterminado `scope_distance = 10` cuando el campo falta y exige un entero no nulo cuando aparece. Un cero explícito se conserva como semilla raíz. El Snapshot sigue en `1.1.0`; la versión del parser distingue la semántica. El esquema admite parser `1.0.0` y `1.1.0`, mientras la validación de aplicación exige que la fuente y versión del Snapshot coincidan. Como el `runId` incluye `parserVersion`, reimportar bytes iguales cambia el ID determinista de ejecuciones creadas por el parser `1.0.0`; los registros ya guardados no se reescriben.

El spike HTTP usa un envelope **propuesto 1.1.0**, [schema separado](http-observation.schema.json); no fingir que el núcleo Nmap v1 ya lo ingiere. Ese gate evita compatibilidad falsa entre contratos distintos.

El grafo interno CHEF `1.4.0` no cambia el Snapshot público `1.1.0`. Conserva el evento BBOT fuente, adapta tipos conocidos a activos/evidencia CHEF y contabiliza los aún no adaptados. `FINDING` se proyecta como candidato. `parent_domain_of`, los servicios `TCP_PORT_HINT`, y la entidad `organization` usan calificación `hint`: dominios padre se derivan de la sección ICANN de la PSL; TCP 80/443 se sugieren para dominios/IP; las URLs aportan su puerto explícito o predeterminado. `chef_org_stub_hints` deriva nombres candidatos desde dominios raíz (`scope_distance = 0`), el campo `stub` de `SOCIAL` y `tenant-names` de `AZURE_TENANT`, con orden determinista, límites y sin red. Para dominios, genera la forma Unicode desde punycode mediante IDNA y su alias ASCII transliterado con `deunicode`; ambos son activos candidatos con evidencia derivada del mismo dominio raíz. La transliteración es funcionalmente equivalente para producir un alias ASCII, aunque la tabla de caracteres puede diferir de Python `Unidecode`. Ningún nombre sugiere propiedad confirmada. Nunca se marca un puerto sugerido como abierto. `DNS_NAME_UNRESOLVED` conserva `unresolved`; los dominios/IP derivados quedan como `hint`, y una observación directa prevalece al fusionarlos. El lector `1.4.0` conserva compatibilidad con `1.0.0`–`1.3.0`; consumidores anteriores rechazan `1.4.0` hasta actualizar su esquema. Los módulos offline solo se ejecutan si se habilitan explícitamente en la configuración o el perfil de importación, y mantienen el linaje. Los registros previos sin `chef_recon_graph` siguen siendo legibles; al reimportar un JSONL se construye la proyección. `npm run check:docs` valida esquema y ejemplo; las pruebas funcionales de equivalencia y controles negativos se aplazan por indicación del propietario.
El perfil `offline_hints` también añade `DNS_NAME_HINT` después de derivar propuestas del lote `DNS_NAME` del proyecto. La salida es una pista de dominio con regla/versión y razones en el localizador; el activo se enlaza con IDs de hasta dos eventos fuente existentes en el mismo grafo. La regla `dns.offline_mutation` versión 4 segmenta palabras concatenadas con un léxico DNS embebido, aplica variantes locales y sugiere 24 nombres comunes incluso desde un dominio raíz importado; por ello los IDs deterministas de candidatos difieren de versiones anteriores, mientras snapshots y grafos ya almacenados permanecen intactos hasta una reimportación. No se cambia el esquema ni la versión del grafo 1.4.0: reutiliza `domain`, `qualification: hint` y `evidenceIds`. El evento nuevo es aditivo en el grafo fuente; los lectores CHEF conservan tipos desconocidos y los muestran en estadísticas por tipo. La lectura de hosts sigue siendo offline; la resolución y verificación quedan desactivadas. La verificación funcional de importación, segmentación, límites y enlaces se aplaza junto con la fase de pruebas solicitada.

La proyección `recon-graph 1.4.0` interpreta `RAW_DNS_RECORD` ya importados de A/AAAA, ANAME, CNAME, MX, NAPTR, NS, PTR, SOA y SRV, más los hosts/IP en `resolved_hosts` serializados en eventos DNS/URL, como relaciones `resolves_to` con evidencia fuente y fecha original. Con `offline_hints`, `chef_dns_rdata_hints` procesa ANAME, CNAME, MX, NAPTR, NS, PTR, SOA, SRV y TXT para emitir hasta 32 nombres canónicos como `DNS_NAME_HINT` con calificación `hint`; A/AAAA solo alimenta relaciones cuando llega como evidencia fuente. La relación describe lo que afirma el registro importado, no una resolución actual; la pista es candidata y tampoco acredita disponibilidad. Ninguna operación consulta DNS ni amplía el scope. El ejemplo `recon-graph.json` incluye una relación A importada y separa su evidencia de las pistas. Las pruebas funcionales positiva/negativa se aplazan con la fase de pruebas indicada por el propietario.

Ejemplo de activación local opcional:

```toml
[modules]
chef_url_parents = true
chef_url_attribute_hints = true
chef_ip_range_expansion = true
chef_dns_parent_hints = true
chef_dns_rdata_hints = true
chef_dns_tlsrpt_hints = true
chef_common_port_hints = true
chef_org_stub_hints = true
chef_dns_mutation_hints = true
```

Una configuración ausente o sin estas claves no ejecuta derivaciones; `active_discovery` debe permanecer deshabilitado. La clave `ScopePolicy` de una importación limita evidencia/proyección y no es permiso para generar tráfico.

La migración a Rust no cambia por sí sola el formato wire. El núcleo Rust debe demostrar conformidad con los mismos fixtures/golden que TypeScript antes de reemplazarlo. Los mensajes IPC de Tauri son contratos internos nuevos: deben versionarse y validar payloads en Rust y TypeScript. El esquema SurrealDB es persistencia interna, no formato de exportación. Cualquier ampliación de snapshot sigue el procedimiento de versión, esquema, ejemplo, prueba y nota de compatibilidad.

`export_chef_web_evidence_report` adapta parcialmente `modules/output/web_report.py` con `web-evidence-report-export 1.0.0` ([esquema](web-evidence-report-export.schema.json), [ejemplo](examples/web-evidence-report-export.json)). La prueba funcional de escape HTML, límites, relaciones y control negativo queda pendiente para la fase indicada por el propietario.

## Exportación explícita de correo

`export_chef_observed_emails` adapta parcialmente `modules/output/emails.py` con `observed-email-export 1.0.0` ([esquema](observed-email-export.schema.json), [ejemplo sintético](examples/observed-email-export.json)). Exporta JSON solo desde eventos existentes de tipo `EMAIL_ADDRESS`, deduplicando la dirección exacta y conservando cada ID de evidencia, fecha y evidencia padre. En React la acción identifica el archivo como dato personal y exige pulsar «Confirmar y descargar»; el destino es exclusivamente local. `scopeStatus: not_asserted` evita presentar como dentro de scope el filtro `in_scope_only` del origen, que CHEF no conserva. No deduce correos a partir de `USERNAME`, no transforma mayúsculas, no publica información a servicios remotos y limita la salida a 2 MiB. No cambia Snapshot ni el grafo persistido. Las pruebas funcionales de deduplicación, evidencia, formato inválido y límites quedan pendientes para la fase indicada por el propietario.

Con `offline_hints`, `chef_dns_tlsrpt_hints` procesa solo TXT `_smtp._tls` ya importados con una etiqueta `v=TLSRPTvN`. La lista `rua` se limita a 32 pistas por registro: `mailto:` produce únicamente un `DNS_NAME_HINT` del dominio, y HTTP(S) un `URL_HINT` del origen, sin ruta, query ni fragmento. Las pistas retienen el evento TXT como padre y usan tipos ya reconocidos por `recon-graph 1.4.0`; Snapshot y el esquema del grafo no cambian. No se consulta DNS/HTTP ni se publican direcciones de correo completas. El módulo de origen desactiva `emit_raw_dns_records` por omisión, así que la importación puede carecer del TXT requerido.
