# CI, CodeQL y gates de integración

Actualizado 29-09-2026. La protección del repositorio combina comprobaciones automáticas y revisión humana. [Quality](../../.github/workflows/quality.yml) ejecuta instalación reproducible, lint, tipos, tests, validación de docs/arquitectura/contratos, formato, auditoría npm y benchmark; su job Java compila/prueba el spike Montoya. [CodeQL](../../.github/workflows/codeql.yml) analiza `javascript-typescript` y `java-kotlin` en push a `main`/`docs`, PR hacia `main`, programación semanal y ejecución manual. Se usa [CodeQL Action v4.38.1](https://github.com/github/codeql-action/releases/tag/v4.38.1) fijado al commit revisado, `security-extended`, permisos `contents: read` y `security-events: write`; Java se compila durante la extracción. [GitHub documenta la configuración avanzada](https://docs.github.com/en/code-security/how-tos/find-and-fix-code-vulnerabilities/configure-code-scanning/configuring-advanced-setup-for-code-scanning).

## Qué bloquea un PR

Antes de solicitar review: `npm ci`, `npm run check`; cambios Java ejecutan Maven `clean verify`. La plantilla exige escenario positivo y negativo, contrato/ADR, fuente/scope, estado real y revisor. CI `Quality` y `Burp spike` existentes, más los dos jobs CodeQL, deben completarse según reglas de protección. Una alerta CodeQL se triagea: corregir, demostrar falso positivo o documentar riesgo pendiente que impide merge; no ocultarla cambiando umbrales. CodeQL detecta patrones conocidos, **no verifica** que los proyectos estén aislados, que no haya falso enlace, que un proveedor tenga permiso o que la UX sea comprensible. La [matriz CWE](../security/cwe-controls.md) asigna pruebas específicas a esos riesgos.

## Operación y límites

El workflow está versionado en Git, pero la **primera ejecución remota** es necesaria para confirmar que GitHub acepta permisos, lenguajes, build Java, subida SARIF y configuración de Code Scanning. Una definición YAML válida/local no equivale a job verde. Revisar resultados en la pestaña de Actions y Security/Code scanning del repositorio público; si el repositorio tiene CodeQL default setup activado, evitar análisis duplicado y documentar cuál se mantiene. Las reglas de protección de `main` deben exigir los nombres de check una vez que el workflow se ejecute; antes no adivinar contextos. Dependabot vigila npm, Maven y Actions por separado, con revisión humana de sus PRs.

**El motor Go no existe aún y no está cubierto por los jobs actuales.** Su primer PR debe agregar `go test ./...`, `go vet`, fixtures de conformidad TS/Go, fuzzing acotado de entrada/reglas y CodeQL `go` al workflow, con build/resultado verificados en GitHub. Para cambios de lenguaje, ruta Maven o paquetes nuevos, actualizar matriz/build-mode y comprobar alcance del análisis. Actualizar el SHA de CodeQL con referencia a release oficial y CI verde. PRs de solo docs siguen validando enlaces, Mermaid, JSON/YAML y formato; CodeQL puede volver a ejecutarse pero no sustituye ese gate. Si Code Scanning falla por configuración/plan de GitHub, registrar el error real y corregirlo antes de declararlo integrado.
