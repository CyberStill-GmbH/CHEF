# Commits, ramas y pull requests de CHEF

Objetivo: cambios pequeños, auditables y fáciles de revertir, con evidencia del comportamiento. Esta guía aplica al equipo y colaboradores externos; [CONTRIBUTING](../../CONTRIBUTING.md) describe el recorrido completo.

## Ramas y commits

Crear una rama corta desde la base vigente y actualizada para cada incremento revisable. Convención: `develop/<componente>` para los incrementos de desarrollo CHEF, por ejemplo `develop/chef-backend-rust-migration` o `develop/chef-local-storage`; usar `fix/<tema>` solo para correcciones urgentes claramente delimitadas. No hacer trabajo directo en `main`. Antes de editar: `git status`, leer [scope](../product/scope.md) y el ADR relevante, y preservar cambios ajenos. Cuando una entrega dependa de otra PR aún no integrada, abrirla como PR apilado contra esa rama; al integrar, actualizar su base a `main` y resolver los conflictos antes de solicitar la revisión final.

Usar mensajes en imperativo y en inglés o español **de forma consistente dentro del PR** con el formato `tipo(área): resultado concreto`. Tipos permitidos: `docs`, `feat`, `fix`, `test`, `refactor`, `ci`, `chore` y `revert`. El asunto identifica el área y resultado; el cuerpo explica motivo, impacto y compatibilidad si el asunto no basta. Ejemplos: `docs(adr): justificar PostgreSQL`; `fix(core): normalizar objetivos DNS`; `test(core): cubrir el control negativo`. Evitar mensajes vacíos (`updates`, `fix stuff`) y mantener el asunto breve. No incluir secretos, datos de clientes ni hashes sensibles. Separar commits por intención revisable y mantener cada commit coherente; no fragmentar una corrección inseparable solo por estética. No reescribir historia compartida ni hacer force-push sin coordinación.

Un cambio de contrato público incluye schema, ejemplo, prueba y nota de compatibilidad en el mismo PR; un cambio de regla incluye fixture positivo/negativo y versión. Un ADR nuevo se abre con [la guía](../adr/README.md), no se edita una decisión anterior para ocultar su historia. La revisión del diff antes de commit verifica que solo hay archivos previstos.

## PR pequeño y review

Una PR debe resolver una historia/decisión y tener descripción que un revisor nuevo pueda entender: **problema/trigger, comportamiento antes/después, alcance real, contrato/ADR afectado, Given/When/Then positivo y negativo, validación ejecutada, riesgos y pendientes**. El título usa el mismo formato `tipo(área): resultado`; enlaza la issue o historia. Incluir capturas solo para UI real y datos sintéticos. Indicar explícitamente si algo es `implementado`, `propuesto` o `validado manualmente`. No mezclar UI, parser, DB y Burp en una PR masiva salvo un corte vertical mínimo que exija integración; dividir por contrato y dependencias. El autor solicita review de alguien distinto: César↔Diego/Jhojan según área, con el [mapa de responsabilidades](../plan/team.md). La inicialización automatizada no sustituye esa revisión.

Gate antes de merge: ejecutar `npm ci` y `npm run check`; para Java/Montoya, `mvn -B -f extensions/burp/pom.xml clean verify` y registrar por separado la matriz manual realizada/pendiente cuando cambie su comportamiento. En GitHub, `main` exige actualmente `Quality` y `Burp spike` verdes, una aprobación de otra persona, aprobación posterior al último push y resolución de conversaciones. La protección exige que la rama esté actualizada; bloquea force-push y borrado. CodeQL se ejecuta en CI y sus alertas pertinentes se revisan, pero **no es hoy un check requerido por la protección de `main`**. No describir checks opcionales como gates obligatorios. Documentar falsos positivos con explicación, no suprimir por conveniencia. El análisis estático no cubre autorización real, falsos enlaces ni UX. Probar scope, evidencia y acceso entre proyectos cuando corresponda. Nunca ejecutar reconocimiento activo solo para “validar CI”.

Responder comentarios con cambio o razón técnica; resolver conflictos sobre la base actual; repetir las comprobaciones afectadas. Mantener el PR en borrador mientras falte implementación, evidencia, revisión o la fase de pruebas aplicable. Integrar solo después de aprobación independiente y checks requeridos verdes. La configuración vigente del repositorio permite **solo squash merge**: dejar un PR autocontenido para que el commit resultante tenga el mismo formato `tipo(área): resultado`, sea fácil de revertir y conserve enlace al PR. No integrar una cadena apilada fuera de orden: primero la PR base, luego actualizar la siguiente sobre `main`. No fusionar directamente ramas de trabajo ni saltarse el PR. No etiquetar release ni anunciar despliegue por haber fusionado documentos. Después de integrar, verificar checks en `main` y que README/enlaces representen el estado real.

La rama `main` es la base de integración. Las ramas de entrega usan `develop/<componente>` según la convención CHEF; si una PR depende de otra todavía abierta, la primera puede apuntar temporalmente a esa rama y debe cambiar a `main` una vez integrada la dependencia. La protección y los permisos se verifican en GitHub: esta guía no afirma que una regla esté activa si la configuración del repositorio no la confirma. Las firmas de commit no son requisito configurado actualmente.

## Plantilla y política de seguridad

La [plantilla de PR](../../.github/PULL_REQUEST_TEMPLATE.md) es el mínimo, no un formulario mecánico. Reportar bugs con versión/commit, fixture sintético mínimo y esperado/observado; vulnerabilidades por [SECURITY](../../SECURITY.md). Para contribuciones de terceros, confirmar licencia MIT del código original y términos de cada fuente/API; una herramienta open source no concede derecho automático a almacenar/redistribuir sus datos.

CHEF adopta esos criterios y mantiene su propia política de rama, checks y squash merge, definida arriba.
