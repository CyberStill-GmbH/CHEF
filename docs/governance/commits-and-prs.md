# Commits, ramas y pull requests de CHEF

Objetivo: cambios pequeños, auditables y fáciles de revertir, con evidencia del comportamiento. Esta guía aplica al equipo y colaboradores externos; [CONTRIBUTING](../../CONTRIBUTING.md) describe el recorrido completo.

## Ramas y commits

Crear una rama corta desde la base vigente y actualizada para cada incremento revisable. Convención: `develop/<componente>` para los incrementos de desarrollo CHEF, por ejemplo `develop/chef-backend-rust-migration` o `develop/chef-local-storage`; usar `fix/<tema>` solo para correcciones urgentes claramente delimitadas. No hacer trabajo directo en la rama protegida de destino. Antes de editar: `git status`, leer [scope](../product/scope.md) y el ADR relevante, y preservar cambios ajenos. Cuando una entrega dependa de otra PR aún no integrada, abrirla como PR apilado contra esa rama; al integrar la PR base, actualizar la base de la siguiente PR a la rama destino vigente y resolver los conflictos antes de solicitar la revisión final.

Usar mensajes claros, concisos y consistentes dentro del PR, con el formato `tipo(área): resultado concreto`. Tipos: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`, `ci`, `chore`. Ejemplos: `docs(adr): justificar PostgreSQL para proyectos multiusuario`; `test(core): fijar control negativo de hostname compartido`; `ci(codeql): analizar TypeScript y Java`. El asunto describe el cambio, no “updates”; el cuerpo explica motivo, impacto y compatibilidad cuando haga falta. No incluir secretos, datos de clientes ni hashes de archivos sensibles.

Cada commit debe quedar compilable o tener una razón explícita para ser parte de una secuencia dependiente; agrupar por intención revisable y dejar pruebas/docs junto al comportamiento que describen. Antes de publicar, revisar `git log`, el diff completo y que no queden commits temporales (`WIP`, `fixup!`, `squash!`) ni cambios ajenos. Si se corrige un commit ya publicado y compartido, añadir otro commit; no reescribir historia aprobada o consumida por otras ramas. El título de la PR debe poder usarse como mensaje final del commit de integración y seguir el mismo formato.

Un cambio de contrato público incluye schema, ejemplo, prueba y nota de compatibilidad en el mismo PR; un cambio de regla incluye fixture positivo/negativo y versión. Un ADR nuevo se abre con [la guía](../adr/README.md), no se edita una decisión anterior para ocultar su historia. La revisión del diff antes de commit verifica que solo hay archivos previstos.

## PR pequeño y review

Una PR debe resolver una historia/decisión y tener descripción que un revisor nuevo pueda entender: **problema/trigger, comportamiento antes/después, alcance real, contrato/ADR afectado, Given/When/Then positivo y negativo, validación ejecutada, riesgos y pendientes**. Incluir capturas solo para UI real y datos sintéticos. Indicar explícitamente si algo es `implementado`, `propuesto` o `validado manualmente`. No mezclar UI, parser, DB y Burp en una PR masiva salvo un corte vertical mínimo que exija integración; dividir por contrato y dependencias. El autor solicita review de alguien distinto: César↔Diego/Jhojan según área, con el [mapa de responsabilidades](../plan/team.md). La inicialización automatizada no sustituye esa revisión.

Gate antes de merge: `npm ci`, `npm run check`; para Java/Montoya, `mvn -B -f extensions/burp/pom.xml clean verify` y matriz manual separada cuando se cambie su comportamiento; CI `Quality`, `Burp spike` y `CodeQL` verdes según archivos. Revisar alertas CodeQL relevantes y documentar falsos positivos con explicación, no suprimir por conveniencia. El análisis estático no cubre autorización real, falsos enlaces ni UX. Probar scope, evidencia y acceso entre proyectos cuando corresponda. Nunca ejecutar reconocimiento activo solo para “validar CI”. No integrar con checks pendientes, fallidos o saltados sin una excepción registrada y autorizada por mantenimiento.

Responder comentarios con cambio o razón técnica; resolver todas las conversaciones; actualizar desde la rama destino mediante rebase cuando sea necesario y repetir las comprobaciones afectadas. Mantener el PR en borrador mientras falte implementación, evidencia o revisión. La integración normal de CHEF es **Squash and merge**: una aprobación independiente, conversaciones resueltas y checks requeridos verdes son condiciones previas; el maintainer verifica el título final del squash y registra el PR como fuente de contexto. Los commits de trabajo quedan en el historial del PR; el historial de la rama destino conserva un commit por PR. No usar merge commits ni integrar manualmente saltando protecciones. No integrar una cadena apilada fuera de orden: primero la PR base, luego rebasar la siguiente sobre su nueva base y pedir revisión final. Si hay una excepción (por ejemplo, una política de release que requiera otra estrategia), documentar motivo y autorización en el PR. Después de integrar, verificar checks en la rama destino y que README/enlaces representen el estado real.

Este flujo sigue prácticas verificables en proyectos mantenidos: cambios acotados, mensajes comprensibles, pruebas locales, atención a CI y conversación de review. Wazuh pide trabajar sobre la rama de desarrollo vigente, enfocar el cambio y atender resultados de CI; sus repositorios pueden tener requisitos particulares de sign-off/licencia. CHEF no exige `Signed-off-by` ni DCO salvo que una política del repositorio lo incorpore explícitamente. Referencias: [guía de contribución de Wazuh Dashboard Reporting](https://github.com/wazuh/wazuh-dashboard-reporting/blob/main/CONTRIBUTING.md) y [estrategias de merge de GitHub](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/about-pull-request-merges).

## Plantilla y política de seguridad

La [plantilla de PR](../../.github/PULL_REQUEST_TEMPLATE.md) es el mínimo, no un formulario mecánico. Reportar bugs con versión/commit, fixture sintético mínimo y esperado/observado; vulnerabilidades por [SECURITY](../../SECURITY.md). Para contribuciones de terceros, confirmar licencia MIT del código original y términos de cada fuente/API; una herramienta open source no concede derecho automático a almacenar/redistribuir sus datos.
